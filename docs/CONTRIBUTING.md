# Участие в разработке

Изменения должны сохранять переносимость, нейтральность и обратимость проекта.

## Подготовка

1. Используйте 64-разрядную Windows 10 или Windows 11.
2. Клонируйте репозиторий.
3. Для runtime-тестов или сборки поместите официальный `zapret-win-bundle` в
   `runtime`.
4. Выполните:

```powershell
.\tools\test-project.ps1 -SkipRuntimeCheck
Invoke-Pester .\tests\unit
.\tests\smoke.ps1
.\tests\integration\foreground-lifecycle.ps1
```

CI использует Pester 5.7.1 и PSScriptAnalyzer 1.24.0 в Windows PowerShell 5.1
и PowerShell 7. Перед отправкой изменения не должно быть ошибок анализатора,
Pester или smoke-проверки.

Foreground-тест создаёт скрытые тестовые консоли и отдельный файл `hosts`.
Он проверяет штатный выход, сбои, Ctrl+C и закрытие окна без установки службы
или изменения системного `hosts`. При ошибке тестовая папка сохраняется для
диагностики.

## Проверки и сборка

`tools\test-project.ps1` проверяет синтаксис, размер компонентов контроллера,
JSON Schema и семантику профилей, blob-ссылки, общие группы правил, списки
доменных/IP-целей, соответствие BAT-файлов профилям, игровые фильтры и состав
защищённой копии службы. Этот скрипт не запускает Pester или PSScriptAnalyzer:
в CI они выполняются отдельными шагами.

Набор Pester покрывает передачу аргументов и специальные символы, версии
сборок, языковые настройки и навигацию, проверку архивов, сохранение
пользовательских данных, обновления и откат между двумя структурами сборки.
Проверка служебной копии в Pester выполняется в тестовой папке без установки
службы. Полный тест службы запускается отдельно на одноразовом Windows runner.

Для runtime аудит исходников использует поля `path` из `runtime\SOURCE.json`,
а переносимая сборка с `metadata/release-manifest.json` — поля `releasePath`.
Размеры и SHA-256 проверяются в обоих случаях. Общий модуль Runtime также
проверяет компоненты при сборке и восстановлении из архива.

```powershell
.\tools\test-project.ps1
.\tools\validate-profiles.ps1
.\tools\build-release.ps1
```

Проверка профилей через `winws2 --dry-run` запускается без прав администратора.
Сборщик создаёт чистый временный каталог, проверяет его, формирует
детерминированный ZIP и сверяет содержимое архива с каталогом по SHA-256.
Устаревшие файлы распакованной сборки удаляются по манифесту
`metadata/release-manifest.json`; исходники остаются источником продуктовых
файлов. Локальные runtime, релизы, журналы и результаты не входят в Git.

### Подготовка публикации

Версия хранится в `metadata/VERSION`, описание — в соответствующей секции
`docs/CHANGELOG.md`. Имя релизного коммита по принятому соглашению:
`Release <VERSION>`. Тег `v<VERSION>` запускает release workflow, который
проверяет совпадение версии, восстанавливает зафиксированный runtime, собирает
ZIP и публикует `TrafficProfileManager.zip`, `SHA256SUMS.txt` и описание.
Создание локального ZIP само по себе ничего не публикует.

## Требования к изменениям

- Считайте корень репозитория единственным источником продуктовых файлов.
- Не редактируйте сгенерированные файлы в `release` вручную.
- Основные тексты интерфейса храните на английском, русский перевод — в словаре
  Console. Основную документацию ведите на русском; краткое английское руководство — в `docs/README.en.md`.
- Не привязывайте описания к конкретному провайдеру или стране.
- Поддерживайте пути с пробелами и апострофами.
- Не создавайте службу или задачу без явного действия пользователя.
- Привязывайте очистку видимого режима к сохранённым PID.
- Никогда не перезаписывайте Windows `hosts` целиком.
- Храните пользовательские данные в `user-*`.
- Считайте новые файлы в `config\profiles` и папки в `config\game-filters`
  распространяемым исходным кодом: они не игнорируются Git и входят в локальную
  релизную сборку. Не помещайте туда приватные данные.
- Не добавляйте сторонние бинарники в историю Git.
- При обновлении runtime фиксируйте точные пути, размеры и SHA-256 выбранных
  файлов в `runtime\SOURCE.json`.
- Не публикуйте сборку с `-SkipRuntimeProvenanceCheck`.

## Профили

- Копируйте близкий готовый профиль, а не создавайте JSON с нуля.
- Используйте уникальный `name`, совпадающий с именем файла.
- Заполняйте `displayName`, `order` и понятное `description`.
- Ссылайтесь на blob-файлы относительными путями внутри `assets`.
- Выполняйте аудит проекта и `tools\Validate Profiles.bat`.
- Описывайте отличие нового профиля от существующих.

Формат описан в [PROFILE_FORMAT.md](PROFILE_FORMAT.md).

## Pull request

Укажите:

- решаемую проблему;
- поведение до и после изменения;
- выполненные проверки;
- менялась ли работа службы, задачи, `hosts` или процессов;
- отчёт сравнения, если менялось поведение профилей.

Не публикуйте журналы с личными именами узлов, именами пользователей,
публичными IP и другими идентификаторами.

## Оформление страницы проекта

Русский README сохраняет общий стиль с центрированным заголовком, бейджами,
эмодзи и таблицами. Краткое английское руководство хранится в `docs/README.en.md`,
проверка скачанной сборки — в `docs/VERIFY.md`. Версия на странице берётся
из GitHub Releases, статус проверок — из workflow `validate.yml` ветки `main`.

Анимация создаётся командой `powershell.exe -NoProfile -File .\tools\build-demo.ps1`.
Скрипт использует Windows PowerShell 5.1 и подготовленный runtime; он не запускает
профиль и не меняет системный `hosts`. Источник и ограничения показанного
сравнения описаны в [media/README.md](media/README.md). При замене примера
сохраняйте дату реального запуска и удаляйте личные данные.
